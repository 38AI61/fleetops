Scope facts (from the constitution — the plan must cover exactly these):

- **D-41 / D-17 seam**: `Fanout` interface with a Redis implementation keeps the seam; no in-process fanout, no embedded NATS. Redis carries `position.batch` and `presence.changed`; NATS core carries `jobs.events.*` and `alerts.*` (GF-4).
- **`position.batch` publish** (roadmap P7; README §3): after each successful flush, ingest publishes the stored points to Redis `positions.batch.<fleet_id>`, **≤ 200 points per message**, points coalesced across the flush batch. The publish hooks the existing `FlushResult.Stored` seam (GF-79) — decide exactly where (Writer vs Consumer vs a decorator) and how failures are handled (fanout is best-effort; WS is not the durable record; record the residual risk). Grouping: a flush can mix fleets — decide per-fleet grouping and whether a chunk may span fleets (it must not; subject carries fleet_id). The batching/chunking must be a pure function so the property test can run without Redis.
- **Presence** (D-20): ingest side — on each accepted message `SET device:<id> online EX <ttl> GET` (single round trip); when the GET returns the old value absent → publish `presence.changed` (online) to `presence.changed.<fleet_id>`. Offline sweeper every 15 s over `vehicles_latest` (`server_ts < now − 120 s`) with in-memory last-emitted state; publishes `presence.changed` offline **once per episode**. Presence is WS-only, not persisted (accepted risk, roadmap §4). TTL default 120 s (`FLEETOPS_PRESENCE_TTL`). Sweeper runs in the ingest process (decide placement and how it coexists with Maintenance). Decide the exact `presence.changed` payload shape (device id, vehicle id, fleet, state, ts) and how the hub relays it (which rooms get it).
- **WS hub** (D-21, tech-stack §7.3): new service `services/ws-hub` (pinned path, tech-stack §3) on local port 10011 (`-addr` default `127.0.0.1:10011`, flag style like the API; **no PORTS.md/compose edits** — the port is already reserved). Endpoint `WS /stream?fleet=<id>`: first-message auth `{"type":"auth","token":…}` within 5 s else close 4401 (text or HTTP-level close — decide and record); token `fleet_id` claim must match `?fleet=` else close; **room cap 2,000 per fleet** (`FLEETOPS_WS_ROOM_CAP`, D-22) → new connection at cap is refused (decide the WS-level expression of "503 at cap" — a websocket upgrade can carry HTTP status: record the mechanism); ping every 20 s, evict after 60 s without pong; close at token expiry (D-03) via a timer at exp. Drivers may connect but receive only `job.updated` for their own jobs (D-21, README §8) — in P7 decide how driver identity maps to jobs (the claim has `sub` = user id and `role`; jobs are not wired yet — record the P7 boundary: e.g. drivers subscribe per-job once P11 lands, or a per-vehicle/driver room; the plan must pick the P7 behavior and record it, no P11 implementation). Hub subscribes NATS core `jobs.events.*` + `alerts.*` (GF-4) and Redis `positions.batch.*` + `presence.changed.*`; relays to rooms keyed by fleet_id. Decide: hub process wiring (config Load reuse — REDIS_URL + NATS_URL; JWT_SECRET needed for token verify), shutdown order, and the exact per-event JSON envelope on the wire (field names/types; README §6 names the four event types).
- **Validation** (roadmap P7): browser-free client receives coalesced batches; connection at cap refused; silent device yields `presence.changed offline` once.
- **Testing** (roadmap P7 + tech-stack §9): **property test on chunking** (every point exactly once, order preserved, each chunk ≤ 200); integration with real Redis and real WS clients (testcontainers); `-race` on hub; **1,000 synthetic connections in CI** (a named test in the hub package; fits alongside P23's 10k).
