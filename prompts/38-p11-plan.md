Open decisions the plan must close and record as **GF-184 onward** (numbering continues at GF-184; highest existing is GF-183), each with rationale, in the P10 spec's decision style:

1. Driver identity: the caller's driver row is resolved from `users.driver_id` (principal `UserID`, fleet-scoped). Decide: what an unlinked driver gets on `today` (proposal: 200 empty list) and on a transition (proposal: 404 — no job can be theirs); that the actor recorded in `job_events` is the user id via the GF-180 mechanism.
2. `today` semantics: "today" evaluated in `fleets.timezone` (the GF-174 day semantics, `(window_start AT TIME ZONE f.timezone)::date = today`); "now" comes from the injectable `Deps.Clock` (the store stays Clock-free; the handler computes the day string). Decide whether undated (`window_start` NULL) non-terminal own jobs are included (proposal: yes — an active job without a window is the driver's current work and must not vanish) and whether terminal states (`delivered`, `failed`, `cancelled`) are excluded (proposal: yes — completed work belongs to reports, P21). Response envelope `{"jobs": [...]}` matching GET /jobs; ordering (proposal: `window_start ASC NULLS LAST, id ASC`). Query parameters on this route (proposal: none are defined; unknown ones are ignored, consistent with `filterFrom`).
3. Route roles: tech-stack §7.1 marks the routes "JWT driver". Decide the role-matrix cells: proposal — all five `/driver/jobs/*` routes are driver-only: admin/manager/dispatcher 403, driver 2xx, unauthenticated 401. Role checks run before body read (GF-28 idiom).
4. Ownership guard: a driver transition requires, inside the store tx (row locked): job in the caller's fleet, `job.driver_id` non-null and equal to the resolved driver id — anything else `ErrNotFound` (404; no existence leak across drivers or fleets). Cross-driver isolation is therefore the same guard the roadmap validation exercises.
5. Endpoint contracts: request bodies — `accept`/`start`/`pickup` accept empty body or `{}` (any field → 400); `fail` requires `{"reason": string}` non-empty, ≤ 1000 runes (match the GF-173 notes cap), unknown fields → 400; malformed `:id` → 404 (the `idParam` idiom). Responses: `200` with the GF-173 job object on applied and replayed calls; error mapping reuses GF-178 (`400 validation_failed`, `404 not_found`, `409 conflict`, 401/403 middleware).
6. Fail persistence: `failure_reason` is written by the same UPDATE as the state change (`UPDATE jobs SET state='failed', failure_reason=$1 WHERE … state=$from`); the trigger allows it (it is not an assignment column); replay is **state-only** per D-24 — a repeated `fail` returns 200 with no event even if the reason differs, and the first reason stays durable. Decide and record exactly this.
7. Store shape: new driver-facing methods on `Store` (proposal: `DriverJobs(ctx, fleetID, driverID int64, day string)` and `DriverTransition(ctx, actor, fleetID, jobID, driverID int64, to State, reason *string)`) — `DriverTransition` reuses `begin`, the row lock, the ownership guard, and `mapWriteErr`; it must remain the only new write path and must not duplicate the D-24 logic differently from `Transition`. Decide whether `Transition` itself stays untouched (proposal: yes) and how `Change`/`Outcome` are reused.
8. NATS publishing for driver transitions: same subject/body as GF-179; `driver_id` is always non-null on driver transitions (a job only reaches `assigned` via `Assign` with a driver). One message per applied transition, none on replay/409, publish after commit. The driver `/stream` consequence: token subject (users.id) vs `driver_id` (drivers.id) — record as a known integration consideration (the hub matches the token subject against the published driver id; the user↔driver identity binding is exercised by seed/PWA phases P13/P23) with **no code change in P11**.
9. Role-matrix rows and fixtures: five new rows; the transition rows need fresh jobs assigned to the driver user's linked driver (a per-row setup hook in the `jobRowSetup` style — create job, assign via the store to a vehicle + that driver, then for start/pickup pre-advance the state).
10. CLAUDE.md rows (mechanical only): extend the Jobs (P10) block with the driver routes, the driver-identity rule, the today semantics, and the fail-reason rule; file stays < 200 lines. No new env vars, make targets, or migrations.
